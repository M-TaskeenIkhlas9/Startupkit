§02 · Why this needs more than one user role

What the adjacent tools don't do

The nearest comparisons are single-purpose: they don't need multi-role access because they don't span a company's whole operating life.

ProductScopeData modelWho else gets access
Stripe AtlasIncorporation + basic banking/Stripe setup — a one-time transactionFormation record, mostly stateless after issuanceNobody by design — single founder, single sitting
Tailor BrandsLLC/brand formation for SMBs — templated, DIYPer-order forms, no persistent company objectNo collaborator model
FondoBookkeeping/tax for startups — ongoing but finance-onlyLedger + filings, accountant-facing on their sideAn accountant sees your books; not a shared platform
StartupKitFull lifecycle — formation → legal → finance → brand → people → GTM → ops, continuouslyOne persistent company object touched by every workflowFounders, teammates, internal support, investors/advisors, external lawyers/accountants — at the same time, on the same record

That last column is the actual architectural driver: because one company object is shared by many domains and many humans who shouldn't see the same slice of it, access control isn't a login gate — it's a first-class part of the data model, checked per resource on every read and write.

§03 · System at a glance

Seven layers, access checked at the edge and enforced at the data layer

Three properties are load-bearing across every layer below, because this platform has to outlive its first five roles, first six integrations, and first database choice:

  • Maintainable — each band below is one bounded service with one job. A bug in the AI Co-Founder service cannot corrupt Company data; it can only call the Company service's interface, same as any other client.
  • Extensible — roles (§05), workflows (W1–W8 today, more later), and integrations (§03 bottom band) are all rows in a table or files in a manifest, not branches in code. Adding a sixth role or a ninth workflow is a data change and a UI update, not a redesign.
  • Component-swappable — every external dependency (incorporation provider, e-sign vendor, LLM, even Postgres-vs-managed-Postgres) sits behind a narrow interface the rest of the system calls generically. Swapping DocuSign for another e-sign vendor, or Anthropic for another model, touches one adapter, not the workflow or document logic that calls it.

§04 · Storage decision

SQLite, Mongo, Postgres, or Supabase?

The company snapshot you're rendering today (CompanySnapshot) is a mix of tabular facts (founders, EIN, jurisdiction) and deeply nested, workflow-specific blobs (Brand core, GTM state, People roles) that change shape as workflows evolve. That's the actual question the database choice has to answer: can one engine hold both well, under many concurrent users, with per-tenant isolation baked in?

OptionConcurrent multi-user writesStructured + flexible (nested) dataTenant isolationOps burdenVerdict for StartupKit
SQLiteSingle-writer file lock — fine for a CLI or a demo, not a multi-founder, multi-role web appNo native JSON querying worth relying onNone built in — you'd hand-roll it per fileLowest — but wrong tradeoff hereRule out
MongoDBGoodNative document model — a natural fit for the nested workflow blobsRoll your own at the app layerA second database to run, back up, and secure alongside whatever holds relational factsOnly if you outgrow JSONB
PostgreSQLExcellentRelational tables and JSONB columns with indexing — one engine covers both shapesNative row-level security (RLS) — policies enforced by the database itself, not just app codeYou run/patch/back up Postgres yourselfStrong default
SupabaseExcellent (it is Postgres)Same JSONB + relational strengthsRLS is a first-class product feature — policies are declared once, enforced everywhere including their auto-generated APIsManaged — backups, connection pooling, point-in-time recovery handled for youRecommended
Recommendation, confirmed by a deeper pass (see below). One database: Postgres, via Supabase to start. Relational tables for founders, workflows, access grants, and audit log; a JSONB column per workflow for the shape-shifting Brand/People/GTM state, indexed with Postgres's GIN indexes where you need to query inside it. Mongo would solve the nested-data half of the problem but reintroduce the exact thing a shared, RBAC-governed company object can't afford: two sources of truth to keep permissioned consistently. Still Postgres even once you add the trickiest data this platform holds — see next.

Applying it: templates, filled documents, and SSN/EIN

The concrete case: founders fill formation and tax templates (Delaware entity docs, IRS forms like the SS-4), download the result, sign it externally (DocuSign or similar), and submit the signed version back for the record. That case is what actually stresses a storage choice — a fixed small template set, an unbounded stream of filled submissions, a document that becomes non-deterministic once it's signed, and PII that a bank-adjacent regulation covers. One engine still handles all of it, but not as one undifferentiated blob:

DataWhere it livesWhy
Templates (fixed set, immutable, tiny)Postgres bytea, cached in app memory on bootSmall fixed volume is the exception case where a second storage system buys nothing — one transaction commits template + metadata together, one backup covers both.
Submission answersPostgres jsonb in submissionsThis — not the rendered file — is the real audit record: template_id + version, the answers, user_id, timestamps, and a SHA-256 hash of the generated output.
Generated (unsigned) outputNot stored — regenerated on demandDeterministic generation (no embedded timestamps or random IDs) means the stored hash proves a later regeneration is byte-identical. Zero storage growth per submission.
Signed, returned artifactObject storage (S3-compatible), referenced from submissions.file_refOnce a founder signs it, it's the actual legal artifact and generation is no longer deterministic — this is the one output that must be retained, not regenerated.
SSN / EINSeparate submission_pii table, application-layer envelope encryption via a real KMSIsolated so it can carry stricter RLS, per-read audit logging, and independent purge — a leaked DB credential alone should never hand over an SSN.
Why this is a compliance question, not just an engineering one. A platform that fills IRS/EIN forms sits in the same regulatory bucket as a tax preparer under the FTC Safeguards Rule — encryption in transit and at rest, MFA, a written security program, and incident response aren't optional. There's no fixed legal retention period for SSN/EIN, but the obligation is real: keep it only while there's a business purpose, document the policy (e.g. "raw SSN/EIN deleted 90 days after filing, or immediately on request"), and enforce it including in backups. None of this changes the database choice — it changes what you do with two columns.
§05 · Access control

RBAC as configuration, not code

You asked for two properties specifically: granting/revoking access at a granular level (down to a workflow or a section), and being able to add a role or change a policy without shipping a code change. Both come from the same design choice — permissions are data, evaluated by one policy engine, not if role == "admin" scattered through the app.

Extensible by construction. A roles table (key, label, default_scope, is_external) backs the five below — they're the seed data, not a hardcoded enum. Adding role six ("Auditor," "Franchisee," whatever comes up) is a new row plus a UI label; the policy engine, the invite flow, and the permission matrix in §06 all read the table, so none of them need a code change to recognize it.

The five roles today

RoleWhoDefault scopeCan narrow to a single workflow?
Founder / OwnerThe person who created the companyEverything, including granting/revoking accessN/A — always full scope
Co-founder / TeamInvited by the owner, works inside the companyFull workspace by defaultOptional — owner can restrict a teammate to specific workflows
Ops / AdminInternal StartupKit staff (support, success)No standing access to any company's dataBreak-glass only: time-boxed, reason-logged, fully audited access to one company
Advisor / InvestorExternal, invited by the founderRead-only: health scores, journey, documents marked shareableAlways scoped — never sees raw PII (EIN/SSN masked) or the input layer
Lawyer / AccountantExternal collaborator, invited for a purposeNothing by defaultAlways scoped — e.g. "W2 IP & Legal only," usually with an expiry

How a permission check actually works

Because the rule is {role, resource, scope, expires_at} stored in a table, adding a role, changing what "Advisor" can see, or revoking one lawyer's access to one workflow are all row edits — through an admin UI or a support tool — never a deploy.

Granularity has two axes: which section (the sidebar groups — Overview, Build, Intelligence, Inputs, plus the two new ones) and, within Workflows, which W-code. The table below is the default policy; every cell is editable per company via §05's access grants.

* Ops/Admin has no standing per-company access — only the Admin console itself, from which a support action opens a logged, time-boxed grant into one company (§08).

  • Founder/Owner — the only role that can create or revoke other grants; sees every masked field unmasked (EIN, SSN, bank tokens' last-4).
  • Co-founder/Team — full workspace by default (most companies are small), but the owner can narrow one teammate to "W7 GTM only" the same mechanism used for external collaborators — it's one policy, not a separate "team" system.
  • Advisor/Investor — a deliberately thin, read-only slice: health score, journey progress, and only documents the founder explicitly flags shareable. No cap table detail, no raw EIN/SSN, no input-layer notes.
  • Lawyer/Accountant — the sharpest scope: one workflow (or one document set), usually with an expires_at, and edit rights limited to comment/approve within that workflow — never company-wide fields.
  • Ops/Admin — inverted from the others: default-deny into any tenant's data, with an explicit, audited break-glass path for support. This protects founders' fiduciary data (EIN/SSN/bank tokens) from casual internal access, which matters as much for trust as for compliance.

§08 · Trust

What holding EINs, SSNs, and bank tokens actually requires

  • Field-level encryption for EIN, SSN, and provider OAuth tokens — encrypted distinctly from ordinary rows, decrypted only for roles whose policy explicitly allows the unmasked field (Founder/Owner; Advisor/Lawyer see masked values only, per §06).
  • Break-glass admin access — Ops/Admin has zero standing access; opening a company's data from the admin console requires a reason, creates a time-boxed grant, and writes to the audit log before the first read.
  • Tamper-evident audit log — every grant, revoke, approval, and document generation is hash-chained; this is also what makes "who saw the SSN, when, and why" answerable.
  • Scoped, rotated integration tokens — banking/e-sign/CRM tokens are per-tenant, least-privilege, and revocable independently of the platform's own auth.
