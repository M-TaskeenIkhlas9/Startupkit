The storage rule, applied everywhere below. One self-managed PostgreSQL instance is the single source of truth. Relational tables for structured facts; JSONB columns for the shape-shifting per-workflow state; bytea for document templates and (for now) the filled/signed document bytes too — there is no separate object store in this version. 1 · Conceptual overview

What is StartupKit, and who does it talk to?

Bird's-eye: the core system, the humans, and the outside services — no internals.

2 · Component level

The seven layers as services

Decompose the core into bounded services and the interfaces between them. Two services everything leans on (Auth&RBAC, Company); five domain services; one data layer.

3 · Sequence

A representative authenticated request

The path every page load and mutation takes — RBAC checked at the edge, enforced again at the row. Shown for "open a workflow & generate a document."

4 · Communication

Same actors, message-numbered

A communication diagram shows the same interaction as the sequence but emphasizes who links to whom, with messages numbered in order rather than laid out on a timeline.

5 · Data-flow (DFD)

Where the data lands

Rectangles are external entities, rounded shapes are processes, cylinders are data stores. All stores are tables/columns in the one PostgreSQL instance.

6 · Deployment

What actually runs, self-managed

The one shared topology. Deliberately minimal: no managed database, no object storage — a PostgreSQL we operate ourselves, on infrastructure we control.

Trade-off we're accepting for now. Self-managing Postgres means we own backups, failover, patching, and connection pooling ourselves — real operational work a managed option would absorb. It's the right call while the schema and team are small and cost/control matter most; the escape hatch is that nothing in the app code assumes anything but plain PostgreSQL, so moving to a managed Postgres later is an ops migration, not a rewrite.
